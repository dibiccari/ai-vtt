- Squeezing, forced moves and flight effects (Nov 2026, rule gaps closed): **Squeezing** (2014 PHB): `reachable()` runs its normal pass with the whole body, then `reachSqueeze()` from every square it found: steps the whole body cannot make but the body one size smaller can, cost doubled (1 extra foot per foot; difficult terrain adds one more). A Large+ creature standing where its whole body does not fit (`bodyFits()`) is marked by `settleBody()` (called after a drag drop and after the DM's moveToken): `token.squeezed`, `fp()` returns one size smaller, the effect `squeezing` (disadvantage on attacks and Dexterity saves, attacks against it have advantage: the DM applies it) and a chat line; it grows back where the body fits. A wall stub inside a 2x2 footprint is therefore squeezable too. Landing checks use the smaller body on narrow squares. **Forced moves**: a token action move with condition `forced` (pushed, pulled, thrown) or `teleport` becomes `moveToken.mode`: no opportunity attack, no movement spent; forced still stops at walls within 120 ft, a teleport ignores walls and distance (lands on the nearest free square). **Effects that fly or hold aloft** are data in public/data/effect-data.json: `fly` (feet or "walk"), `aloft` (stays up when knocked prone, held...), `still` (no sideways movement), `speedBonus` (feet): fly, potion of flying (walking speed, hover), wings of flying (60, falls like a flyer), levitate (hovers, speed 0, concentration, up to 20 ft), longstrider (+10 ft, doubled by haste). `flySpeedOf()`, `heldAloft()`, `effectiveSpeed()` read them; removing such an effect checks for a fall. **End triggers outside a fight**: `noteRollLines()` finds the creature a DM roll line is about by name (not only the active combatant), so sanctuary ends on an attack line and **guidance** (trigger `check-rolled`) ends on an ability check line (not a saving throw); **slow** (trigger `turn-save`) reminds the DM at the end of its holder's turn to roll the Wisdom save and remove it on a success (the table does not roll it: the caster's DC is not on the board). Mage armor ending when armor is put on stays with the DM (the table cannot tell). Tests: browser 'squeezing by the book', 'flight and speed effects by name', 'end triggers outside a fight...', 'forced and teleported moves'; free test in test/dm-expand.test.mjs; dm-check steps forced and levitate (Boots of levitation in the inventory) pass live ($0.20).

- Doors the DM can work (Nov 2026): a door wall `{type:'door', open, locked?, secret?, dc?}` in the map config (`normalizeMapConfig` keeps the flags on doors only; a secret door is never saved open). Locked = the table will not open it (a click shows 'The door is locked' and tells the DM in `tableNotes` which door was tried); secret = drawn and treated as plain wall (not clickable, blocks sight and movement whatever its open flag) until revealed. The chat request carries the walls with the flags and the server adds `doors` to the board state (`doorsForPrompt()`: n by order in the wall list, at [col,row], state open|closed|locked|secret, dc, near = the closest place pin within 4 squares). DM token action `door` (value = the door's number, condition open|close|lock|unlock|reveal; one more enum value, schema probe OK) becomes `doorAction`; the table opens a closed unlocked door, refuses (and tells the DM) to open a locked or secret one, lock closes and locks, reveal prints 'A hidden door is revealed'. A padlock marks locked doors on the table; Map Test has a Doors list (Normal/Locked/Secret and the dc; orange dots locked, purple secret) and its Open/Close tool respects both. Prompt paragraph 'Doors:' (check for locked doors, passive Perception or a roll for secret ones, never mention a secret door). - Nothing applied twice (Nov 2026, the user: "I want to be sure that nothing ever gets double committed"). Two layers, both in memory on the server and both tested (test/idempotency.test.mjs, free and offline; live steps setcoins, payonce, payonce2, rewarditem, rewarditem2, rewardxp, rewardxp2 pass). (1) **Exactly once per request**: the browser gives every message to the DM a `requestId` (`newRequestId()` in public/js/tabletop/chat.js); `lib/request-ledger.js` remembers finished and running IDs (15 minutes, at most 300). The same ID again gets the first answer back (`replayed: true`) and changes nothing; a copy while the first is being worked on gets 409; a request that failed is forgotten so it can be sent again; only the request that started the work may finish or release its entry (a refused copy must not). A page that goes away aborts the model call and releases the entry (see the abort in routes/ai-dm.js). (2) **No identical reward on the next replies**: `lib/reward-guard.js` records the rewards of the last two replies per campaign (positive coins, XP, an item added; never spending, purchases, `setcoins` or removals) and refuses an identical one for the same target, reporting it in `characterProblems` ("Skipped (already applied on the last replies): +10 gp for Edric...") which the table prints and the next history shows the DM as `[Table skipped: ...]`; a model that keeps repeating keeps being refused; Start over (`POST /api/campaigns/:id/start-over`) resets it.
